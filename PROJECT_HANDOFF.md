## 5. Catalogue and recommendation rules

At the last generation: **261 cards, 20 issuers, 29 populated categories, 96 comparison pages and 431 sitemap URLs**. These are computed counts, not constants to preserve when the catalogue legitimately changes.

Important card fields:

- Identity: `id`, `name`, `issuer`, optional variant/product-group fields, `network`.
- Facts: `annualFee`, `annualFeeAmount`, joining-fee equivalents, `rewardLine`, `highlights`, optional structured welcome/milestone/lounge/exclusion/redemption/forex/fuel details.
- Evidence: `sourceUrls`, `verifiedOn`, official product/application URL, optional image provenance.
- Availability: `active`, `applicationsOpen`, `recommendationEligible`, `availabilityNote`, `eligibilityNote`, `secured`.
- Editorial hints: `bestFor`, `feeType`, `minSpend`, `creditReq`, `editorial` summary/ideal audience/strengths/trade-offs/verdict/alternatives.
- Partner configuration and drafts are admin concerns; public serialization must not expose them.

`cards_seed.py` hashes the repository catalogue and refreshes it on startup when required. It preserves `adminManaged` cards and archives known legacy demo IDs rather than deleting user records. This means a repository edit may **not** replace a conflicting admin-managed record; inspect the relevant record before assuming a deployment updates it.

Recommendations exclude inactive, application-closed and explicitly recommendation-ineligible cards. The quiz cannot establish an invitation, banking relationship or professional-segment eligibility. Review `restricted_access.py` whenever eligibility behavior changes.

`rating` is an editorial compatibility baseline, not an aggregate customer rating. Community ratings are separate, moderated and not published until the minimum review count is met. Confidence is a fit indicator, not approval probability.

Value estimates are editorial scenarios, not precise guaranteed cashback. They consider supplied spending, documented fees, waiver thresholds, labelled monetary welcome benefits and illustrative lounge value. Preserve the regression that a ₹600 voucher requiring ₹10,000 spending counts ₹600, not ₹10,000. Preserve comma handling for ₹1,00,000 waiver thresholds and finite/bounded numeric parsing. Do not interpret reward points as rupees or infer missing issuer terms.

Comparison pairs are generated only when both cards' maintained editorial alternatives refer to one another. Do not generate arbitrary all-pairs pages merely for search traffic.

When updating a card: verify official sources; update availability, relevant facts and `verifiedOn` honestly; review affected editorial text; sync static fallbacks; regenerate public pages; test scoring, links and metadata. A source-verification date is not a launch or publication date.

## 10. Deployment and rollback

Frontend workflow: `.github/workflows/deploy-pages.yml`.

- Pushes to `main`, manual dispatch and a scheduled refresh trigger it.
- Installs Yarn dependencies, runs frontend tests and builds React.
- Push builds generate from the repository catalogue. Scheduled/manual refreshes may read the live catalogue through the configured API URL.
- Runs generated-page tests and the SEO audit, then uploads/deploys GitHub Pages artifacts.
- GitHub variable `CARDIQ_BACKEND_URL` overrides the default API origin.

Backend: `.do/app.yaml` tracks `main` with `deploy_on_push=true`, source `/backend`, Dockerfile `backend/Dockerfile`. Live runtime secrets/environment belong in DigitalOcean. Preserve existing variables when editing them; do not replace the whole list. The Docker image explicitly copies application files so local `.env` files do not enter it.

Deployment checklist:

1. Inspect local/remote state and isolate intended changes. Verify no secrets, private exports or unrelated docs are included.
2. Run appropriate tests/build/generated-page checks. Review migrations and the effect of catalogue seeding on admin-managed cards.
3. Publish a reviewed commit to `main` using authorized credentials. If CLI authentication fails, an authorized GitHub API connector can create blobs/tree/commit and update the ref with the expected current SHA. Preserve file bytes/number formatting and reject stale-head updates; do not reserialize the whole catalogue unnecessarily.
4. Wait for **both** Pages publication and backend rollout. They complete independently.
5. Verify production `GET /api/ready`, representative card/metadata pages and the specific corrected behavior. Prefer read-only checks; do not create customer records or send emails as a smoke test.
6. Inspect Actions results. Record the commit and any failed/nonblocking checks honestly. Do not claim all checks passed merely because Pages succeeded.

Latest release references:

- Commit: https://github.com/neerajgarg1109/app/commit/806061dfd7b5190fdc6f09253aadc106ea4a839f
- Frontend deployment: https://github.com/neerajgarg1109/app/actions/runs/40629305660
- Operations verification: https://github.com/neerajgarg1109/app/actions/runs/40629305698

For rollback, prefer a reviewed revert of the relevant code commit and normal deployments. A code rollback does not roll back customer writes, admin publications, provider sends or database indexes. Changing the database/origin is not a routine rollback; preserve writes and verify migration requirements first. Admin card rollback stages a historical snapshot for review and publication rather than silently replacing production facts.

## 12. Open work: highest priorities

See [the full code review](docs/code-review-2026-10-28.md). These were **not resolved by the latest deployment**:

1. **P1 — Shared-result ownership.** Public result IDs also authorize lead mutation and result-email requests. A shared-link recipient can change the associated contact record; email actions lack owner capabilities/send limits. Separate read-only sharing from a hashed owner capability and plan migration for existing results. Removing recipient email from API responses reduced disclosure but did not solve authorization.
2. **P2 — Outbound request safety.** Application-link checks validate initial URL syntax then follow redirects. Restrict actual network egress/DNS and every redirect; hostname-only checks do not defeat DNS rebinding. Do not probe production/internal endpoints to demonstrate this.
3. **P2 — Abuse protection and legacy reminders.** Public writes need verified distributed rate limiting. The legacy abandoned-quiz sender now requires consent, but its delivery loop still needs an atomic claim/ledger to prevent duplicate sends from concurrent admin requests.
4. **Editorial quality.** Review catalogue-derived comparisons for distinct, useful guidance. Do not increase indexed page count merely to target keywords. Maintain official evidence and meaningful benefit qualifications.
5. **Search/performance evidence.** Search Console coverage, queries, rankings and Google-selected canonicals were not inspected; field Core Web Vitals/Lighthouse were not measured. Technical metadata checks do not guarantee ranking improvements.
6. **Dependency/production verification.** The latest review did not perform a third-party vulnerability scan or verify live network policy. Operations CI passed on the final release, but long-running production load and disaster recovery remain separate tasks.

Do not confuse these open items with the fixes already deployed: draft serialization/publication leakage, review/campaign concurrency, old unsubscribe-link validity, blank admin-token access, recipient-address response leakage, voucher/spend parsing, comma-formatted waiver thresholds, non-finite numeric inputs, routine analytics-index rebuilds, stale shared-result display and missing reminder consent were addressed and regression-tested.
